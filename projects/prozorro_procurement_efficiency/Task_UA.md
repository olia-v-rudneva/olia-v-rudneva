# Варіант 3. Prozorro: аналіз ефективності публічних закупівель на реальних відкритих даних

**Стек:** Python (requests, pandas, numpy, scipy.stats) → PostgreSQL → Tableau Public
**Рекомендована назва папки:** `prozorro_procurement_efficiency`

---

## Чому саме цей варіант

З трьох кандидатів (RFM+LTV, юніт-економіка й ціноутворення, реальні відкриті дані) обрано **реальні дані Prozorro**, і ось чому. RFM та юніт-економіка тематично дублюють те, що в портфоліо вже закрито — когорти, retention, LTV, ARPPU вже показані у двох проєктах, і третій кейс на ту саму логіку додасть мало. А от **усі п'ять наявних проєктів побудовані на навчальних або синтетичних даних**. Це помітно рекрутеру: дані вже чисті за задумом, схема відома, обсяг зручний. Робота з реальним відкритим API — це інший клас задач: пагінація й ліміти, вкладений JSON, нестандартизовані найменування, пропуски, дублі, зміна структури полів у часі, необхідність самому вирішити, що вважати одиницею аналізу. Плюс тема закупівель — це буквально економіка підприємства й контроль витрат, тобто вона грає на той самий фах автора, що й варіант 1, але з іншого боку: не «як планували витрати всередині», а «як витрачають публічні гроші назовні». І це єдиний варіант, у якому висновки стосуються реального світу, а не згенерованого.

## 1. Бізнес-сценарій

Аналітичний відділ громадської організації (або внутрішній аудит розпорядника бюджетних коштів) досліджує ефективність закупівель однієї товарної категорії — **закупівлі палива (дизельне пальне та бензин А-95)** — комунальними підприємствами та органами місцевого самоврядування за 2023–2025 роки.

Питання, на які потрібні відповіді:

> **1. Скільки бюджет реально економить на конкурентних процедурах — і чи варта економія тих термінів, які вони забирають?**
> **2. Чи однакову ціну за літр платять різні замовники в один і той самий місяць — і чим об'єктивно пояснюється розкид?**
> **3. Де конкуренція фактично відсутня, і скільки це коштує бюджету?**

Тема має просту й перевірювану економічну логіку: пальне — гомогенний товар з публічною ринковою ціною, тому **різниця в ціні за літр між замовниками майже повністю є різницею в якості закупівлі, а не в якості товару**. Це рідкісний випадок, коли порівняння цін між організаціями коректне — і саме тому категорія обрана.

**Користувач:** Сергій, аналітик відділу моніторингу. Йому потрібен дашборд, який показує, у яких замовників ціна за літр систематично вища за медіану ринку, і на яку суму.

> ✅ Дані **реальні та відкриті**. Це єдиний проєкт портфоліо на непідготовлених даних.

## 2. Вхідні дані

### 2.1. Основне джерело — відкритий API Prozorro

Публічний API працює без ключа й без реєстрації.

- **Фід змін (список тендерів):**
  `GET https://public-api.prozorro.gov.ua/api/2.5/tenders?descending=1&limit=1000`
  Повертає сторінки з `id` та `dateModified` плюс `next_page.offset` для наступної сторінки. Прохід ведеться курсором по `offset`, а не по номеру сторінки.
- **Картка тендера:**
  `GET https://public-api.prozorro.gov.ua/api/2.5/tenders/{tender_id}`
  Повертає повний JSON: замовник, предмет, класифікатори, лоти, пропозиції, договори.
- Дзеркало / альтернативний хост: `https://public.api.openprocurement.org/api/2.5/tenders`.
- **Готові вигрузки та БІ-модуль:** `bi.prozorro.org` — якщо повний прохід фіда виявиться надто довгим, звідти можна взяти агрегований зріз за категорією. Набори також публікуються на `data.gov.ua` (пошук «публічні закупівлі», розпорядник — ДП «Прозорро»).

> Перед початком роботи перевірити актуальну версію API та назви полів у документації: `prozorro-api-docs.readthedocs.io`. Структура JSON між версіями відрізняється, і це частина задачі.

**Фільтрація категорії.** Відбір вести за **класифікатором CPV (ДК 021:2015)**, а не за текстом назви:
- `09134200-9` — паливо дизельне
- `09132000-3` — бензин
- (за потреби розширити до групи `09130000-9` — нафта і дистиляти)

Текстовий пошук по `title` використовувати тільки як контрольну перевірку повноти відбору — назви предметів закупівель у різних замовників записані по-різному («Пальне дизельне», «ДП», «паливо дизельне Євро-5», «талони на пальне»), і це один із перших реальних сюрпризів у даних.

## 3. Метрики та формули

### 3.1. Економія

**Абсолютна економія на процедурі:**
```
savings_uah = expected_value − award_value
```
**Відносна економія:**
```
savings_pct = (expected_value − award_value) / expected_value × 100
```
За групою (метод / регіон / місяць) — **зважена економія**, не середня з відсотків:
```
savings_pct_weighted = Σ(expected_value − award_value) / Σ expected_value × 100
```
> Просте середнє від `savings_pct` дає неправильну відповідь: закупівля на 8 тис. грн отримує таку саму вагу, як закупівля на 8 млн. Це обов'язково пояснити в README — типова помилка, на якій видно різницю між «порахував» і «розуміє».

### 3.2. Ціна за одиницю (ядро аналізу)

```
unit_price_uah = award_value / quantity          (тільки де unit ∈ {л, літр, l})
unit_price_net = unit_price_uah / 1,20           якщо vat_included = true
unit_price_usd = unit_price_net / nbu_rate(contract_date)
```

**Відхилення від ринку** — по кожній процедурі відносно медіани того ж місяця:
```
month_median = median(unit_price_net) за місяцем контракту
price_deviation_pct = (unit_price_net − month_median) / month_median × 100
overpayment_uah = (unit_price_net − month_median) × quantity    (якщо > 0)
```
Медіана, а не середнє — розподіл цін має викиди, і середнє ними зсувається.

### 3.3. Конкуренція

```
avg_bids = середня кількість пропозицій
single_bid_share = процедур з bids_count ≤ 1 / усі процедури × 100
non_competitive_share = сума за reporting + negotiation / загальна сума × 100
unsuccessful_rate = процедур зі status = 'unsuccessful' / усі × 100
```

**Концентрація постачальників — індекс Херфіндаля-Хіршмана:**
```
HHI = Σ (частка постачальника i у сумі закупівель, у %)²
```
Трактування: `HHI < 1500` — конкурентний ринок, `1500–2500` — помірна концентрація, `> 2500` — висока. Рахувати HHI по кожному регіону окремо — і показати, що між регіонами є різниця в разах.

### 3.4. Ефект конкуренції (статистична частина)

Основна перевірювана залежність: **чи зростає економія з кількістю пропозицій?**

- Побудувати `savings_pct` як функцію `bids_count` (1, 2, 3, 4, 5+) — боксплоти по групах.
- **Кореляція Спірмена** між `bids_count` і `savings_pct` (непараметрична — розподіл економії асиметричний, з масою в нулі).
- **Тест Манна–Вітні** для двох груп: `bids_count = 1` проти `bids_count ≥ 3`, з 95 % довірчим інтервалом для різниці медіан (bootstrap, 10 000 ресемплів).
- **Оцінка «вартості відсутньої конкуренції»:**
```
lost_savings = Σ_{процедури з bids_count ≤ 1} expected_value × (savings_pct_median[bids≥3] − savings_pct_median[bids≤1]) / 100
```
Тобто: скільки бюджет міг би зекономити, якби неконкурентні процедури пройшли з нормальною конкуренцією. Це головна цифра проєкту.
- Обов'язкове застереження в README: **це кореляція, не причинність.** Можливе зворотне пояснення — дрібні та специфічні закупівлі і притягують менше учасників, і дають меншу економію. Перевірити, контролюючи розмір: повторити порівняння окремо в межах однієї сумової групи (квартилі `expected_value`).

### 3.5. Терміни

```
cycle_days = contract_date − date_published
```
Порівняти за методами процедур. Це дає відповідь на питання 1: економія проти швидкості.

## 4. Покроковані вимоги

### Крок 1. Збір даних (Python)
1.1. Скрипт `01_fetch_prozorro.py`: прохід фіда курсором по `next_page.offset`, збереження ID у локальний файл.
1.2. Завантаження карток тендерів із **обов'язковими**: паузою між запитами (`time.sleep`), повторними спробами з експоненційною затримкою на 429/5xx, логуванням помилок у окремий файл.
1.3. **Інкрементальність:** зберігати `dateModified` останнього обробленого запису, щоб перезапуск не починався з нуля. Сирі JSON зберігати локально (`data/raw/*.json.gz`) — щоб аналіз не залежав від доступності API і був відтворюваним.
1.4. Фільтр за CPV і періодом; вивантаження у плаский CSV `data/tenders_flat.csv` (грануляція: один рядок = тендер × лот × item).
1.5. У README вказати дату вигрузки — реальні дані змінюються, і без дати результати неперевірювані.

### Крок 2. Очищення (це основна робота проєкту)
2.1. **Одиниці виміру.** Привести `unit` до літрів: у даних зустрічаються `л`, `літр`, `Літр`, `l`, `шт` (талони!), `кг`, `тонна`, `послуга`. Рядки, які не конвертуються однозначно, **виключити й порахувати, скільки відсотків обсягу втрачено** — не тихо відкинути.
2.2. **ПДВ.** `valueAddedTaxIncluded` буває `true` і `false` у межах однієї категорії. Без нормалізації ціна за літр відрізняється на 20 % — і весь аналіз розкиду цін стає сміттям. Це перша пастка, яку треба знайти й описати.
2.3. **Замовники.** Один замовник фігурує під різними написаннями назви. Дедуплікація **тільки за ЄДРПОУ** (`buyer_edrpou`), назва — для відображення. Перевірити ЄДРПОУ на валідність (8 або 10 цифр, ведучі нулі не втрачені при читанні CSV — читати як `str`).
2.4. **Постачальники** — так само за ЄДРПОУ; окремо порахувати, скільки постачальників мають кілька варіантів назви.
2.5. **Викиди цін.** Знайти ціни за літр, фізично неможливі (0,5 грн/л — помилка в кількості; 50 000 грн/л — кількість вказана в тоннах при `unit = л`). Правило відсікання: за межами [P1; P99] у межах місяця, з окремим переліком і причиною по кожному викиду.
2.6. **Дублі.** Один тендер може повертатися кілька разів у фіді через `dateModified`; дедуплікація за `tender_id` із залишенням останньої версії.
2.7. **Багатолотові процедури.** Вирішити й задокументувати: аналіз ведеться на рівні лота (правильніше) чи тендера (простіше). Для лотів `expected_value` беруть із лота, не з тендера.
2.8. **Скасовані та невдалі процедури** виключаються з розрахунку економії, але залишаються в аналізі `unsuccessful_rate`.
2.9. Скрипт `02_clean.py` + окремий звіт про якість даних: скільки рядків вилучено на кожному кроці, з причиною (data lineage у вигляді таблиці).

### Крок 3. Завантаження в PostgreSQL і аналітичний SQL
3.1. Схема `prozorro`: `tenders`, `lots`, `items`, `bids_summary`, `awards`, `contracts`, `dim_buyer`, `dim_supplier`, `dim_cpv`, `dim_date`, `nbu_rates`.
3.2. `03_analysis.sql` — ланцюг CTE з метриками розділу 3.
3.3. Обов'язково віконні функції:
- медіана ціни за місяцем: `PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY unit_price_net) OVER (PARTITION BY contract_month)`
- ранг замовників за середнім відхиленням від медіани: `RANK() OVER (ORDER BY avg_deviation DESC)`
- частка постачальника в регіоні: `SUM(...) OVER (PARTITION BY region)`
- динаміка ціни замовника проти попередньої закупівлі: `LAG(unit_price_net) OVER (PARTITION BY buyer_edrpou ORDER BY contract_date)`
3.4. Окрема вітрина `mart_buyer_scorecard`: один рядок на замовника — кількість процедур, сума, середня економія, середнє відхилення ціни, частка одноучасникових процедур, HHI постачальників, оцінена переплата в грн.

### Крок 5. Дашборд у Tableau Public
Мінімум два екрани.

**Екран 1 — «Ефективність»:**
5.1. KPI: `Загальна сума закупівель`, `Економія (грн і %)`, `Середня кількість пропозицій`, `Частка одноучасникових`, `Оцінена переплата`.
5.2. Лінія: медіанна ціна за літр по місяцях (у грн і в умовних доларах, dual axis) + коридор P25–P75 як area — показує, наскільки розкид цін ширший за самий рух ринку.
5.3. Боксплот: `savings_pct` за кількістю пропозицій (1 / 2 / 3 / 4 / 5+).
5.4. Стовпчики: економія та середня кількість пропозицій за типом процедури.
5.5. Scatter: `bids_count` × `savings_pct`, розмір точки = сума закупівлі, з лінією тренду.
5.6. Фільтри: період, регіон, тип процедури, CPV, діапазон суми.

**Екран 2 — «Замовники»:**
5.7. Карта України: середнє відхилення ціни від медіани по областях.
5.8. Таблиця-скоркарта замовників (з `mart_buyer_scorecard`), відсортована за оціненою переплатою; умовне форматування.
5.9. Drill-down / filter action: клік на замовнику → перелік його процедур із ціною за літр, датою, кількістю учасників і постачальником.
5.10. Окремий блок: топ-постачальники й HHI по регіонах.

### Крок 6. Оформлення
6.1. README у форматі решти портфоліо + обов'язкові розділи: дата вигрузки даних, методика нормалізації (ПДВ, одиниці, дефлятор), звіт про якість даних, межі висновків.
6.2. Окремий файл `DATA_SOURCES.md` з точними URL, параметрами запитів і версією API.
6.3. Висновки: 3–5 інсайтів, кожен із цифрою й із зазначенням, що з нього **не** випливає.
6.4. Скрипти й ноутбуки — з можливістю повного перезапуску; сирі дані не комітити цілком (тільки очищений CSV + скрипт збору).

## 5. Джерело даних

**Реальні відкриті дані, без реєстрації й без ключів.**

1. **Prozorro Public API 2.5** — `https://public-api.prozorro.gov.ua/api/2.5/tenders` (дзеркало: `https://public.api.openprocurement.org/api/2.5/tenders`). Документація: `prozorro-api-docs.readthedocs.io`. Містить повний життєвий цикл кожної процедури: оголошення, очікувана вартість, класифікатори CPV, лоти й номенклатуру з кількостями та одиницями виміру, пропозиції учасників, рішення про переможця, підписані договори з сумами й датами, скарги. Ліцензія — відкриті дані, вільне використання з зазначенням джерела.
2. **БІ-модуль Prozorro** — `bi.prozorro.org` — готові агрегати й вигрузки; резервний шлях, якщо повний прохід фіда за 3 роки виявиться надто довгим.
3. **data.gov.ua** — набори ДП «Прозорро» (пошук «публічні закупівлі»); варіант для пакетного завантаження замість API.
4. **API НБУ** — `https://bank.gov.ua/NBUStatService/v1/statdirectory/exchange?json&date=YYYYMMDD` — офіційний курс валют на дату, для приведення цін різних років до порівнянного вигляду.

**Що робить ці дані цінними для портфоліо:** їх ніхто не готував під навчальну задачу. Одиниці виміру не стандартизовані, ПДВ вказаний по-різному, назви замовників пишуться як заманеться, у полі «літри» іноді лежать талони, а кількість буває вказана в тоннах. Тобто етап очищення тут не декоративний — він і є основна складність, і саме він відрізняє реальну роботу аналітика від курсової.

**Резервна тема на тих самих джерелах**, якщо пальне виявиться незручним (наприклад, надто багато закупівель через талони): закупівлі продуктів харчування для навчальних закладів (CPV група `15000000-8`) — там теж гомогенні позиції з публічною ціною і той самий інструментарій.

## 6. Що це додає в портфоліо

- **Єдиний проєкт на реальних, непідготовлених даних** — закриває загальну слабкість портфоліо, де всі п'ять кейсів побудовані на навчальних або синтетичних наборах. Для роботодавця це сигнал, що автор здатен працювати з тим, що є, а не тільки з тим, що дали.
- **Python як інженерний інструмент, а не тільки як pandas у зошиті:** робота з REST API, пагінація, ретраї, інкрементальне завантаження, парсинг вкладеного JSON, побудова відтворюваного ETL. Це помітно вище за поточний рівень секції `projects/python/`.
- **Статистика в прикладному вигляді:** непараметричні тести, bootstrap-довірчі інтервали, контроль на третю змінну, чесне розмежування кореляції та причинності — другий після варіанта 2 спосіб закрити відсутність статистики, але на живих даних.
- **Економічна експертиза в новому розрізі:** нормалізація ПДВ, зважена (а не проста) економія, приведення цін різних років через курс, HHI як міра концентрації — це набір інструментів економіста, а не просто «порахував середнє». Плюс тема публічних закупівель релевантна для роботи в державному й громадському секторі та в міжнародних проєктах.

## 7. Орієнтовний обсяг роботи

| Етап | Годин |
|:---|:---|
| Вивчення API, документації, структури JSON, вибір категорії й CPV | 6–8 |
| Скрипт збору даних (пагінація, ретраї, інкрементальність) | 8–10 |
| Розбір JSON у плаский вигляд, перший погляд на дані | 5–6 |
| Очищення: одиниці, ПДВ, ЄДРПОУ, викиди, дублі, лоти | 12–16 |
| Завантаження в PostgreSQL, схема, аналітичний SQL, вітрина замовників | 10–12 |
| Статистична частина (Спірмен, Манна–Вітні, bootstrap, контроль на розмір) | 6–8 |
| Дашборд у Tableau (2 екрани, карта, скоркарта, drill-down) | 12–14 |

| **Разом** | **67–84 години** (≈ 3–4 тижні при 3 год/день) |

Найдорожчий із трьох варіантів — і найбільша частина часу піде на очищення, а не на аналіз. Це нормально й це треба чесно написати в README: саме такий розподіл часу й буває в реальній роботі.

## 8. Критерії приймання

- [ ] Дані завантажені безпосередньо з відкритого API Prozorro скриптом, який лежить у репозиторії; вказана дата вигрузки.
- [ ] Скрипт збору витримує перезапуск: є інкрементальність, ретраї та логування помилок.
- [ ] Відбір категорії зроблений за CPV, а не за текстом назви; повнота відбору перехресно перевірена текстовим пошуком.
- [ ] Обсяг після очищення — ≥ 10 000 процедур або ≥ 3 роки за однією областю; обсяг вказаний у README.
- [ ] Є таблиця якості даних: скільки рядків вилучено на кожному кроці й чому.
- [ ] Нормалізовано ПДВ (`valueAddedTaxIncluded`) — і в README пояснено, чому без цього аналіз цін недійсний.
- [ ] Одиниці виміру приведені до літрів; частка невідновлюваних рядків порахована й названа.
- [ ] Замовники й постачальники дедупліковані за ЄДРПОУ; ЄДРПОУ прочитані як текст без втрати ведучих нулів.
- [ ] Викиди цін виявлені, перелічені й пояснені причинно (а не просто відсічені).
- [ ] Зафіксовано й обґрунтовано рівень аналізу: лот чи тендер.
- [ ] Ціни різних років приведені до порівнянного вигляду через курс НБУ (або інший обґрунтований дефлятор).

- [ ] Порахована «вартість відсутньої конкуренції» в гривнях, з описом припущень розрахунку.

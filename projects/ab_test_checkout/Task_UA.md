## 1. Бізнес-сценарій

E-commerce магазин побутової техніки. Продуктова команда припускає, що сторінка оформлення замовлення втрачає покупців через довгу форму: 6 обов'язкових полів і обов'язкову реєстрацію перед оплатою.

Розробили нову версію checkout: 3 обов'язкових поля, гостьова покупка без реєстрації, оплата в один екран. Запустили A/B-тест на 21 день: 50/50 випадковий розподіл нових сесій.

Перед командою два питання:

> **1. Чи справді нова сторінка підвищує конверсію в замовлення — або різниця в межах випадковості?**
> **2. Якщо підвищує — чи не впав при цьому середній чек?** Гостьова покупка без реєстрації може приваблювати дрібніші замовлення, і тоді зростання конверсії не окупиться.

Друге питання критичне: рішення приймається не за конверсією, а за виторгом. Тест, у якому конверсія +1,5 п.п., а середній чек −12 %, треба відхилити.

**Замовник аналізу:** Дмитро, Head of E-commerce. Йому потрібне одне рішення — **розкатувати / не розкатувати / продовжити тест** — і аргумент, який витримає питання «а ви впевнені, що це не випадковість?».

## 3. Метрики

### 3.1. Первинна метрика (на ній приймається рішення)

**Конверсія в замовлення (Conversion Rate, CR):**

```
CR_group = кількість сесій з converted = True / загальна кількість сесій у групі
```

Одиниця аналізу — сесія. Це треба зафіксувати **до** аналізу й обґрунтувати: якщо один користувач має кілька сесій, спостереження не є незалежними, і p-value буде заниженим. Обов'язково порахувати частку користувачів з >1 сесією; якщо вона < 5 %, аналіз на рівні сесій допустимий із зауваженням, якщо більша — переходити на рівень користувача (`user_id`, ознака «зробив хоча б одне замовлення»).

### 3.2. Вторинна метрика (контрольна, continuous)

**Середній чек (Average Order Value, AOV):**

```
AOV_group = Σ order_value_uah / кількість замовлень  (тільки is_refunded = False)
```

### 3.3. Похідна бізнес-метрика (для остаточного рішення)

**Виторг на сесію (Revenue per Session, RPS):**

```
RPS_group = Σ order_value_uah / кількість сесій = CR × AOV
```

Саме RPS вирішує конфлікт між метриками: якщо конверсія зросла, а чек упав, RPS показує сумарний ефект у гривнях.

### 3.4. Допоміжні метрики (для діагностики, не для рішення)

- `Checkout Reach Rate` = сесії з `reached_checkout` / усі сесії — перевірка, що змінилося саме те, що змінювали
- `Checkout Completion Rate` = `converted` / `reached_checkout` — конверсія самої сторінки
- `Items per Order`
- `Refund Rate`

## 4. Покроковані вимоги

### Крок 0. Постановка гіпотез (до будь-яких обчислень)

0.1. Сформулювати в ноутбуці **до** першої агрегації:

- **H₀:** `CR_variant = CR_control` — нова сторінка не змінює конверсію
- **H₁:** `CR_variant ≠ CR_control` — двобічна альтернатива

Обґрунтувати вибір двобічного тесту: односторонній дав би вужчий критерій, але приховав би ризик погіршення, а він реальний (спрощена форма може підвищити кількість помилок у даних доставки).

0.2. Зафіксувати рівень значущості `α = 0,05` і цільову потужність `1 − β = 0,80`.
0.3. Зафіксувати одиницю аналізу (сесія або користувач) і пояснити вибір.
0.4. Зафіксувати **практично значущий мінімум**: наприклад, менше за +0,5 п.п. конверсії не варте витрат на розкатку та підтримку. Це MDE, який задає бізнес, а не статистика.

### Крок 1. Валідація тесту (до аналізу метрик)

Цей крок — найважливіший і найчастіше пропущений. Якщо тест не валідний, будь-який p-value нижче безглуздий.

1.1. **SRM (Sample Ratio Mismatch)** — перевірка, чи розподіл 50/50 не зламався. Критерій хі-квадрат на відповідність очікуваним частотам:

```
χ² = Σ (O_i − E_i)² / E_i ,   df = 1
E_i = N_total × очікувана частка групи (0,5)
```

Порогове значення для SRM беруть суворішим за звичайне: **p < 0,001 → тест вважається зламаним**, аналіз метрик не проводиться, поки причина не знайдена. Причини: помилка в спліт-системі, фільтрація ботів по-різному в групах, кешування.

1.2. **Балансування груп за коваріатами.** Порівняти розподіли `device`, `traffic_source`, `region`, `is_new_user` між групами: хі-квадрат незалежності для кожної категоріальної ознаки. Врахувати, що при 4 перевірках на α = 0,05 одна «значуща» різниця очікувана випадково — не робити з неї висновків без поправки.

1.3. **Перевірка цілісності даних:**
- дублі `session_id`;
- сесії, що потрапили в обидві групи (`user_id` з різними `group` — розбіжність спліту);
- замовлення без відповідної сесії та сесії з `converted = True` без замовлення;
- `converted = True` при `reached_checkout = False` (неможлива комбінація).

1.4. **Динаміка по днях.** Побудувати графік кількості сесій і конверсії по днях у кожній групі. Перевірити: чи не було днів із нульовим трафіком в одній групі, чи немає стрибка на початку (див. novelty effect у розділі 6).

### Крок 2. Описова статистика

2.1. Зведена таблиця: група × (сесії, замовлення, CR, AOV, RPS, медіана чека, стандартне відхилення чека).
2.2. Графік: CR по групах зі стовпчиками помилок (95 % ДІ).
2.3. Гістограма й boxplot розподілу `order_value_uah` по групах — до будь-яких тестів. Візуально оцінити асиметрію та хвіст: чеки майже завжди логнормальні з довгим правим хвостом, і це визначить вибір тесту в кроці 4.
2.4. Кумулятивна конверсія по днях для кожної групи — показати, як оцінка стабілізується з часом.

### Крок 3. Тест для конверсії (первинна метрика)

3.1. **Z-тест для двох пропорцій** (основний):

```
p̂_1 = x_1/n_1 ,  p̂_2 = x_2/n_2
p̂_pool = (x_1 + x_2) / (n_1 + n_2)
SE_pool = sqrt( p̂_pool (1 − p̂_pool) (1/n_1 + 1/n_2) )
z = (p̂_2 − p̂_1) / SE_pool
p-value = 2 × (1 − Φ(|z|))
```

Реалізувати через `statsmodels.stats.proportion.proportions_ztest` і продублювати розрахунок «руками» на numpy — щоб було видно, що формула зрозуміла, а не тільки виклик функції.

3.2. **Хі-квадрат незалежності** на таблиці 2×2 (група × конвертувався) — як перехресна перевірка. Показати, що `χ² ≈ z²` при df = 1, і пояснити, чому це одна й та сама перевірка.

3.3. **Довірчий інтервал для різниці пропорцій** (не pooled — для ДІ використовується незважена оцінка):

```
SE_unpool = sqrt( p̂_1(1−p̂_1)/n_1 + p̂_2(1−p̂_2)/n_2 )
95 % ДІ = (p̂_2 − p̂_1) ± 1,96 × SE_unpool
```

Додатково — **відносний ефект (lift)** з ДІ:

```
lift = (p̂_2 − p̂_1) / p̂_1
```

3.4. Назвати в тексті, що означає ДІ, і що він **не** означає (не «з вірогідністю 95 % істинне значення тут»).

### Крок 4. Тест для середнього чека (вторинна метрика)

4.1. Перевірити передумови t-тесту:
- нормальність розподілу чеків: візуально (Q-Q plot) + тест Шапіро-Вілка на підвибірці (на n > 5 000 він відкидає нормальність практично завжди — це треба явно зазначити й не робити з цього трагедію);
- рівність дисперсій: тест Левена.

4.2. **Welch's t-test** (t-тест без припущення рівних дисперсій) — основний вибір для чеків:

```
t = (x̄_2 − x̄_1) / sqrt( s²_1/n_1 + s²_2/n_2 )
df (Welch–Satterthwaite) = (s²_1/n_1 + s²_2/n_2)² / [ (s²_1/n_1)²/(n_1−1) + (s²_2/n_2)²/(n_2−1) ]
```

95 % ДІ для різниці середніх: `(x̄_2 − x̄_1) ± t_{crit, df} × SE`.

4.3. **Тест Манна–Вітні (U-test)** — як робастна перевірка. Обов'язково письмово обґрунтувати, **що саме** він перевіряє: не різницю середніх, а зсув розподілів / вірогідність того, що випадковий чек з однієї групи більший за випадковий з іншої. Тому він не заміняє t-тест, коли бізнес питає про виторг — виторг залежить від середнього, не від медіани.

4.4. Обробка викидів: описати правило (наприклад, відсікання за 99-м перцентилем або winsorize) і **показати результат тесту і з викидами, і без**. Якщо висновок змінюється — це сам по собі результат, який треба доповісти.

4.5. Додатково: t-тест на логарифмі чека (`log(order_value)`) як варіант для логнормальних даних, з поясненням, що тоді порівнюються геометричні середні.

### Крок 5. Потужність і MDE

5.1. **Апостеріорна (post-hoc) оцінка MDE** — який мінімальний ефект тест був здатний виявити за фактичного розміру вибірки:

```
MDE = (z_{1−α/2} + z_{1−β}) × sqrt( 2 p̄ (1 − p̄) / n_per_group )
```
де `z_{0,975} = 1,96`, `z_{0,80} = 0,84`, `p̄` — базова конверсія контролю.

5.2. **Необхідний розмір вибірки** для заданого MDE (обернена формула):

```
n_per_group = ( (z_{1−α/2} + z_{1−β})² × 2 p̄ (1 − p̄) ) / MDE²
```

Продублювати через `statsmodels.stats.power.NormalIndPower().solve_power()` з `effect_size = proportion_effectsize(p1, p2)`.

5.3. Побудувати графік: необхідний розмір вибірки як функція MDE (крива). Позначити на ньому фактичний розмір вибірки — так видно, які ефекти тест міг і не міг зафіксувати.

5.4. Відповісти на питання: **якщо результат незначущий — це «ефекту немає» чи «вибірки не вистачило»?** Відповідь читається з MDE і з ДІ: якщо ДІ повністю лежить у межах практично незначущих значень — ефекту справді немає; якщо ДІ широкий і включає бізнесово важливі значення — вибірки не вистачило.

### Крок 6. Пастки, які треба явно розібрати в ноутбуці

Окремий розділ. Кожен пункт — не абзац теорії, а перевірка на даних або зафіксоване рішення.

6.1. **Peeking (підглядання).** Побудувати графік p-value за кожен день накопичувально й показати, що він перетинав 0,05 і повертався назад. Висновок: тест не можна зупиняти за першим досягненням значущості, бо це роздуває вірогідність помилки I роду набагато вище за 5 %. Зафіксувати, що термін тесту (21 день) визначався заздалегідь розрахунком розміру вибірки.

6.2. **Множинні порівняння.** Порахувати, скільки гіпотез перевірено всього (первинна + вторинна + зрізи по device/source/region). Застосувати поправку Бонферроні (`α_adj = α / m`) або Бенджаміні–Хохберга до зрізів і показати, які «значущі» зрізи після поправки перестають бути значущими. Сформулювати правило: рішення приймається за **однією заздалегідь оголошеною первинною метрикою**, зрізи — тільки джерело гіпотез для наступного тесту.

6.3. **Novelty effect.** Порівняти ефект у перший тиждень і в третій тиждень окремо. Якщо ефект спадає — новизна, і довгостроковий приріст менший за спостережений. Окремо перевірити ефект на `is_new_user = True` (їх новизна не стосується) проти повернених користувачів.

6.4. **Викиди.** Показати вплив кількох найбільших замовлень на AOV: перерахувати AOV без топ-5 чеків у кожній групі. Одне замовлення на 180 000 грн здатне перевернути висновок про чек — це треба продемонструвати числом.

6.5. **Повернення (refunds).** Показати, що висновок змінюється, якщо рахувати виторг з повернень і без. Обґрунтувати, яку версію взяти за основну (чистий виторг, `is_refunded = False`).

6.6. **Порушення незалежності спостережень** — повернутися до одиниці аналізу з кроку 0.3 і перевірити фактичну частку користувачів з кількома сесіями.

**Логіка генерації:**

1. **Обсяг:** ≈ 90 000 сесій за 21 день, ≈ 2 100 сесій/день на групу, спліт 50/50 (з навмисним невеликим перекосом — див. аномалії).
2. **Конверсія:** базова `CR_control = 5,8 %`. Істинний ефект варіанта: `CR_variant = 6,5 %` (+0,7 п.п., lift ≈ +12 %) — навмисно вибрано так, щоб ефект був на межі MDE. Тоді результат не буде тривіальним, і крок 5 (потужність) стане змістовним, а не формальним.
3. **Модифікатори конверсії** (щоб зрізи були реалістичні): `mobile` конвертує в ~0,75 від `desktop`; `paid_search` гірше за `organic`; `email` найкраще. Ефект варіанта закласти **сильнішим на mobile** (спрощена форма більше допомагає на малому екрані) — це має знайтися у зрізах як гіпотеза.
4. **Чек:** логнормальний розподіл, `ln(order_value) ~ N(8,3; 0,62)` → медіана ≈ 4 000 грн, середнє ≈ 4 850 грн, довгий правий хвіст. У варіанті середнє нижче на ~3 % (гостьові покупки дрібніші) — величина навмисно замала, щоб бути статистично незначущою, і це головний методичний урок: «незначуще» ≠ «однакове», але й ≠ «підтверджене погіршення».
5. **Дні тижня:** трафік у вихідні на 20 % нижчий, конверсія на 8 % вища — щоб денна динаміка мала сезонність і аналіз по днях був не рівною лінією.
6. **Повернення:** 3 % замовлень, з дещо вищою часткою у варіанті (5 %) — гостьові покупки повертають частіше.

**Навмисно закладені проблеми:**

- **B1. Novelty effect:** у перші 4 дні ефект варіанта подвоєний (+1,4 п.п.), далі спадає до істинних +0,7 п.п. Аналіз «весь період разом» дасть завищену оцінку.
- **B2. Легкий SRM:** розподіл 50,8 / 49,2 замість 50/50. Хі-квадрат на 90 тис. сесій дасть p ≈ 0,01 — тобто значущо на α = 0,05, але вище порога 0,001. Правильна реакція: не зупиняти аналіз, але зафіксувати як застереження і назвати можливу причину. Це складніший і реалістичніший випадок, ніж явно зламаний тест.
- **B3. Один день (12-й) із технічним збоєм:** у контролі втрачено ~40 % сесій. Треба знайти на графіку денної динаміки й вирішити, що робити (виключити день з обох груп — і показати, як це впливає на результат).
- **B4. Три викиди-замовлення** на 150–200 тис. грн (корпоративні закупівлі), два з них — у варіанті. Без відсікання вони роблять AOV варіанта вищим за контроль; з відсіканням — нижчим. Висновок про чек буквально перевертається.
- **B5. ~150 сесій з `user_id`, що зустрічається в обох групах** — порушення спліту, треба знайти й вирішити (виключити цих користувачів).
- **B6. ~60 сесій з `converted = True` при `reached_checkout = False`** — неможлива комбінація, дефект трекінгу.
- **B7. Незбалансованість за `traffic_source`:** частка `email` у варіанті трохи вища, бо email-кампанія стартувала посеред тесту. Треба виявити хі-квадратом і згадати як обмеження (ідеальне рішення — CUPED або стратифікація, і достатньо назвати цей інструмент як напрямок, не реалізовуючи).

Альтернатива генерації: взяти відкритий датасет **Kaggle «A/B Testing» / «Cookie Cats»** і пройти ту саму методику на реальних даних. Мінус — там немає керованих аномалій, і частину кроків (SRM, novelty) не буде на чому показати. Тому основний варіант — генерація, з відкритим скриптом у репозиторії.

## 6. Що це додає в портфоліо

- **Закриває повну відсутність статистики:** гіпотези, p-value, довірчі інтервали, потужність, MDE, поправки на множинні порівняння — жодного з цих понять портфоліо зараз не містить.
- **Підтверджує заявлений у CV навик «A/B Testing»,** який сьогодні нічим не підкріплений. Це прямий ризик на співбесіді: навик у списку, якого немає в роботах.
- **Робить Python інструментом готового результату,** а не курсових зошитів: `projects/python/README.md` зараз сам чесно пише, що Python ще не стоїть за жодним завершеним кейсом.
- **Демонструє інженерну акуратність аналітика:** валідація тесту до аналізу метрик, розділення статистичної та практичної значущості, чесна відповідь «вибірки не вистачило» замість підгонки висновку.
